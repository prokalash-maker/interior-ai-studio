# Передача изменений для Antigravity

## Новое требование пользователя — Gemini Bridge (10.11.2026)

Пользователь просит полностью переработать Gemini Bridge и повысить автоматизацию. Целевой процесс: для одной комнаты загрузить несколько белых/clay-ракурсов, один раз утвердить общий визуальный дизайн, затем переключать ракурсы так, чтобы материалы и добавленные дизайнерские решения сохранялись согласованно — по рабочей логике Artlantis/3ds Max, где назначенные материалы остаются в сцене при смене камеры.

Это требование добавлено в `PROJECT_PLAN.md` (этап 5.3) и `DEVELOPMENT_ROADMAP_V2.5.md` (приоритет 2). Оно ещё не реализовано. Текущие master-дизайн, карта материалов по поверхностям и привязка генераций к ракурсам — только фундамент.

### Прогресс реализации — 10.11.2026

- В `src/views/GeminiBridgeView.tsx` исправлена изоляция настроек проектов: при переключении проекта Bridge загружает его утверждённый master-профиль либо сбрасывает поля к стартовым значениям. Раньше при переходе в проект без master оставались материалы, стиль, свет, декор и другие параметры предыдущего проекта, что могло незаметно загрязнить новую дизайн-сессию.
- При переключении также очищаются состояние импорта, сообщения и изменённый prompt; открывается первый ракурс выбранного проекта. Схема БД, сохранённые проекты и IPC-контракты не менялись.
- Список ракурсов теперь показывает цветной статусный индикатор: только исходный clay, импортирован результат или этот вид является design master. Добавлены tooltip и легенда статусов на русском, украинском и английском; данные проекта не меняются.
- В `src/types/project.ts` добавлен `ProjectDesignDraft`, отделённый от `ApprovedProjectDesign`. Черновик содержит текущие настройки комнаты, стиля, материалов по поверхностям, света, камеры и prompt-ограничений, но не содержит больших изображений или ссылок на master.
- В `src/services/db.ts` добавлено чтение/запись черновика, а в `electron/main.cjs` — nullable SQLite-колонка `design_draft_json` с `ALTER TABLE` миграцией для существующих баз. Старые базы получают пустую колонку; старые backup JSON остаются импортируемыми, поскольку поле необязательное и экспорт проекта сериализует остальные проектные данные вместе с черновиком.
- В `src/views/GeminiBridgeView.tsx` поля проекта автосохраняются после короткой паузы и восстанавливаются отдельно от утверждённого master. Статус автосохранения показан в UI. При сборке prompt актуальная карта поверхностей и настройки проекта имеют приоритет над деталями изображения master, чтобы сохранённый референс не спорил с новым текстовым выбором пользователя.
- Изменение не мигрирует и не удаляет пользовательские изображения; новая колонка содержит только компактный JSON настроек. Следует вручную проверить: изменить материалы и стиль, дождаться «Настройки сохранены», переключить проект, вернуться и убедиться, что черновик восстановлен, а утверждённый master-референс не изменился. Дополнительно проверить импорт старого backup без поля `designDraft`.
- Этот шаг закрывает один риск межпроектного переноса настроек, но не заменяет требуемую ручную проверку на нескольких проектах и ракурсах.
- После этих изменений `npm run build` прошла: TypeScript, Vite и подготовка Electron завершились успешно. Первый обычный запуск renderer-сборки в ограниченной среде ранее остановился на `EPERM realpath`; разрешённый повтор прошёл. `npm run dist` не запускался, инсталлятор не пересобирался.

### Что предстоит спроектировать и реализовать

1. Единый профиль дизайна комнаты, независимый от отдельных изображений: отделка/цвет/фактура/направление рисунка по поверхностям, освещение, мебель, декор и неизменяемые условия архитектуры.
2. Данные каждого ракурса отдельно: собственный clay-исходник и камера, генерации и утверждённый результат, локальные исключения. Правка вида не меняет общий профиль без явного утверждения пользователем.
3. Переработанный Bridge с рабочим списком видов, общей картой решений, мастером добавления видов, подготовкой референсов/prompt, сравнением кандидатов, утверждением результата для вида и отдельным обновлением общего master.
4. Автоматизация рутинных шагов: наследование настроек новым видом, пакетная подготовка ракурсов, обнаружение скачанного изображения, предварительная привязка к проекту и ракурсу и подтверждаемый импорт.
5. Миграции и проверка сохранности при перезапуске, резервном копировании и восстановлении; RU/UK/EN и ручная приёмка минимум на 3–4 видах комнаты.

### Техническая граница

Gemini Bridge работает с изображениями и не назначает настоящие UV-текстуры на 3D-сцену. Согласованность достигается общим сохранённым профилем, master-референсом и передачей текущего clay как геометрии конкретного ракурса; результат модели остаётся вероятностным. Точное поведение 3ds Max/Artlantis потребует 3D-геометрии/UV или отдельной CAD/3D-интеграции. Любая автоматизация Gemini Web должна оставаться пользовательски управляемой: пользователь входит, отправляет запрос и скачивает результат; запрещены чтение cookies/паролей, private API и обход ограничений.

При продолжении сначала изучить этот раздел, затем этап 5.3 в `PROJECT_PLAN.md`, приоритет 2 в `DEVELOPMENT_ROADMAP_V2.5.md` и актуальные правила в `CODEX_INSTRUCTIONS.md`. Не отмечать функциональность выполненной до реализации и приёмки.

## Изменения кода

### Новая задача продукта — единый дизайн для серии ракурсов (03.11.2026)

- Пользователь загружает несколько белых/clay-рендеров одной комнаты с разных камер. Утверждённая визуализация первого вида становится мастер-референсом дизайна, а не источником камеры или геометрии следующих видов.
- Следующие генерации должны сохранять в видимых областях назначения и характер материалов, палитру, свет, декор и добавленные предметы в правильном масштабе относительно сцены. Каждый текущий clay-кадр остаётся главным источником камеры, перспективы и архитектуры.
- Дизайн хранится как отдельная карта проекта (назначение материалов по поверхностям, цвет/фактура, освещение, декор, ограничения и локальные исключения), а не только как длинный prompt.
- Утверждение/смена мастер-версии — явное действие; импорт нового результата сам по себе не перезаписывает мастер или ранее утверждённые ракурсы.
- На момент постановки задачи `GeminiBridgeView.tsx` выполнял handoff одного изображения. В продолжении 03.11 добавлена базовая модель нескольких видов и мастер-референса; требуется практическая приёмка серии ракурсов.
- Требования и критерии приёмки записаны в `HANDOVER_FOR_CODEX.md` и `PROJECT_PLAN.md`.

### Новая задача — больше автоматизации Gemini Bridge без API (03.11.2026)

- `GeminiBridgeService.openGeminiWeb()` теперь открывает отдельное Electron окно с постоянным `persist:interior-ai-gemini` partition; вход остаётся на стороне пользователя, cookies/пароли не читаются. Есть внешний браузер как fallback.
- Для `will-download` в сессии Gemini изображения PNG/JPG/WEBP сохраняются в `userData/InteriorAIStudio/GeminiBridgeDownloads`; UI показывает обнаруженный файл и предлагает импорт в выбранный проект/ракурс. Размер чтения ограничен 100 МБ, IPC проверяет realpath папки и тип файла.
- В проекте добавлены `views_json`, `approved_design_json`, а в generations — `view_id` с миграциями старой SQLite. Bridge позволяет добавлять/выбирать несколько исходных ракурсов, хранить для каждого ссылку на результат, явно утверждать мастер-дизайн, копировать его визуальный референс и задавать локальное исключение для выбранного вида.
- Мастер хранит текстовые поля стиля/материалов/света/декора и ID материалов. При смене ракурса prompt назначает текущему clay-кадру роль источника геометрии, а мастер-изображению роль style/material anchor. Встроенный интерфейс отдельно говорит, что мастер нужно приложить вторым изображением.
- Чтобы не дублировать большие готовые картинки в `views_json`, результат хранится через `GenerationRecord` и `view_id`; мастер ссылается на соответствующую генерацию. Исходные виды сохраняются в коллекции проекта.
- Добавлены переводы Gemini Bridge для RU/UK/EN: встроенное окно, ошибки, скачивание, импорт и multi-view элементы.
- Electron 34 реализует persistent session и событие загрузки, однако совместимость входа Google во встроенном Chromium зависит от Google; внешний браузер оставлен как fallback. Автоматическая отправка prompt/чтение страницы Gemini не реализованы.
- Electron позволяет слушать события скачивания в конкретной session и выбрать путь загрузки; это подходит для сохранения результата, но не гарантирует автоматическое распознавание нужного изображения, пока Google UI не даёт стабильного идентификатора.
- Gemini Apps Help сообщает про загрузку нескольких изображений, ручной пункт Download full size и доступность 1K без AI-плана / 2K с AI-планом на момент записи. Доступное разрешение следует определять по фактически скачанному файлу; не обещать 4K и не апскейлить незаметно.
- Автоматическая отправка через скрытые DOM-селекторы и private endpoints не входит в безопасный план: интерфейс нестабилен, а автоматизированный доступ не должен нарушать ограничения сервиса. Первая версия должна быть полуавтоматической и управляемой пользователем.
- Требования были добавлены в `HANDOVER_FOR_CODEX.md` и `PROJECT_PLAN.md`; базовая полуавтоматическая реализация уже внесена (см. раздел реализации ниже).

### `src/services/ai/ComfyUIProvider.ts`

- Размер рабочего холста рассчитывается по соотношению сторон исходника; размеры округляются до кратных 8. Ранее фиксированный 16:9 холст растягивал кадры с другим соотношением сторон.
- Пороги Canny изменены с `0.05 / 0.20` на `0.25 / 0.55`, чтобы меньше реагировать на мелкий шум clay-рендера.
- Depth ControlNet получает карту глубины от установленного препроцессора, а не исходный RGB-кадр. Наличие и схема входов проверяются через `/object_info`; основной вариант — `DepthAnythingV2Preprocessor` с небольшим ViT-S checkpoint, запасной — MiDaS. Если препроцессор недоступен, Depth ControlNet пропускается.
- Промпт для SDXL сокращён и переставлен: назначения материалов идут первыми, затем стиль/сцена, свет и фотостандарты. Это снижает риск того, что CLIP обрежет важные указания в конце текста. Ручная директива из prompt добавляется отдельно, если есть.
- Негативный промпт приложения теперь в начале исключает смешанные/нежелательные белые фасады. Приложение всегда передавало собственный negative prompt, поэтому fallback в provider этого не обеспечивал.
- При `preserveGeometry: true` используется исходный кадр через `VAEEncode`, даже если включён `usePureEmptyLatent`. Пустой латент применяется только для творческого режима без сохранения геометрии: тест показал, что пустой латент заставляет модель заново придумывать мебель и часть планировки.
- Значение denoise по умолчанию снижено для режимов provider: strict `0.42`, balanced `0.52`, creative `0.70`. В интерфейсе стартовое значение — `0.65`; пресеты изменены на `0.60 / 0.75 / 0.82` (strict / balanced / creative) по результатам реальных прогонов.

### Диагностика `invalid_request` в OAuth (10.11.2026)
- Пользователь прислал скриншот ошибки из «Настройки → Google OAuth»: после входа Google приложение показывало общий `invalid_request`. Ошибка формируется при HTTP-обмене OAuth code на token, а прежний интерфейс отбрасывал поле `error_description`, поэтому фактическая причина была скрыта.
- Обмен authorization code и обновление refresh token теперь принимают необязательный `client_secret`. Settings и стартовое окно входа показывают отдельное password-поле; значение передаётся только в main process и хранится в DPAPI-шифрованной `secure_kv`. Оно сохраняется и для последующего refresh. Это совместимый вариант: секрет необязателен, по документации Google Desktop client — публичный клиент и не может хранить секрет конфиденциально; приложение не встраивает общий секрет.
- Ошибки token endpoint теперь включают `error_description`, чтобы следующий отказ показывал точный текст Google. Возможное отсутствие client_secret — гипотеза, согласующаяся с некоторыми свежими сообщениями об OAuth Desktop; окончательный диагноз требует повторного входа с текущим Client ID и отображённого текста. Google в документации всё ещё помечает client_secret необязательным.
- Обновлена типизация bridge IPC и RU/UK/EN строки. После реализации нужно запустить `npm run build:renderer`, `npm run build:electron`, `node --check electron/main.cjs`, `node --check electron/googleAuth.cjs`, `node --check electron/preload.cjs`, `node scripts/check-i18n.cjs`; перед installer ожидать ручного подтверждения входа. #### Причина и границы

- OAuth client ID/secret относятся к настройке Desktop OAuth приложения, а не к индивидуальному пользователю. Теперь они могут попадать в release staging, чтобы клиент приложения не просил каждого пользователя создавать OAuth credentials. Это всё равно публичный desktop client: включённый client secret не является конфиденциальной защитой. PKCE остаётся важной мерой протокола. Реальный sign-in и конфигурация consent screen ещё не проверены.
- Gemini Bridge остаётся контролируемым пользователем сценарием. Не добавлялись чтение cookies, паролей, private API, автокликеры, обход лимитов или автоматическая отправка запросов.
- Существующие типы уже включают project views, утверждённый дизайн, design draft/variants и карту материалов по поверхностям; Bridge формирует инструкции на основе утверждённого master-дизайна. Это не эквивалент UV-текстурам общего 3D-проекта и не гарантирует одинаковый материал на каждом ракурсе. Нужен ручной многоракурсный тест.
- В текущем UI генерации ComfyUI/API события выполнения не подключены. Подтверждён только локальный endpoint-прокси; до добавления подписки на Comfy `/ws` не показывать проценты. Inpaint/маскирование/автоматическая сегментация не считаются реализованными, пока не подтверждены узлы и модели живого ComfyUI.
