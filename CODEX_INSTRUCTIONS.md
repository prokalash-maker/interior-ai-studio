Этот файл задаёт рабочий контекст для Codex и других помощников, которые продолжают разработку приложения в этой папке.

## Текущий курс

- Основной рабочий продукт сейчас — приложение из этого репозитория: Electron + React + TypeScript + Vite.
- Продолжать развивать его итеративно, сохраняя уже полезные функции и рабочие сценарии.
- Не начинать параллельную перепись приложения на Tauri/Rust. Возможный перенос на другой desktop-движок — отдельный будущий этап, когда текущая версия будет стабилизирована и пользователю будет понятен план миграции.
- До отдельного решения не удалять Electron, не заменять стек и не создавать второй конкурирующий интерфейс в `D:\AI\Project\New AI PROGRAM`.
- Перед изменением крупной архитектуры, схемы данных или поведения сохранения сначала кратко описать предлагаемое решение и последствия для существующих данных.

## Цель продукта

Помочь архитектору получить интерьерную визуализацию из белого/clay-рендера Archicad или другого 3D-редактора. Основной пользовательский сценарий:

1. Выбрать PNG/JPG/WEBP белого рендера и проверить его превью.
2. Задать комнату, стиль, материалы, освещение и то, что можно или нужно изменить.
3. Просмотреть и при необходимости отредактировать инструкции для выбранного движка.
4. Получить визуализацию через доступный провайдер.
5. Сравнить исходник и результат, при необходимости уточнить результат, сохранить или экспортировать его.

Ключевой приоритет — предсказуемая работа с исходной геометрией и назначением материалов. Ни промпт, ни ControlNet, ни режим интерфейса не гарантируют точного сохранения геометрии. Не писать в UI и документации обещания вроде «100% Geometry Lock» или гарантированного фотореализма.

## Текущий стек и устройство

- Windows desktop: Electron 34, React 19, TypeScript, Vite 6.
- Основной процесс Electron: `electron/main.cjs`; безопасный мост renderer/main: `electron/preload.cjs`.
- UI: `src/`, включая `src/views/GenerationStudioView.tsx`.
- Сборка промптов: `src/services/promptBuilder.ts`.
- AI-провайдеры: `src/services/ai/`; локальный ComfyUI — основной бесплатный путь, Gemini Bridge — опциональный ручной сценарий, прямые облачные API — только необязательные.
- Данные и файловые операции: `src/services/db.ts`, `src/services/storageService.ts`, Electron IPC и база проекта.
- Основные справочные документы: `HANDOVER_FOR_CODEX.md`, `ANTIGRAVITY_HANDOFF.md`, `DEVELOPMENT_ROADMAP_V2.5.md`, `PROJECT_PLAN.md`, `TECHNICAL_ARCHITECTURE.md`, `ARCHICAD_INTEGRATION.md`, `RISKS_AND_MITIGATIONS.md`.

Перед каждой новой задачей прочитать этот файл, затем целевые документы и исходники по затрагиваемому сценарию. Handoff-файлы считать журналом и историческим источником, а не автоматическим доказательством, что каждая описанная функция сейчас работает.

## Правила разработки

- Работать в рамках конкретного пользовательского сценария и доводить его до цельного, обозримого результата. Не ограничиваться несвязанной микроправкой, если пользователь просит продолжать разработку.
- Сначала выяснять существующее поведение и переиспользовать подходящие компоненты, типы и сервисы. Не переписывать архитектуру целиком без необходимости.
- Не менять формат БД, IPC-контракты, структуру файлов проектов и экспортируемые типы без оценки совместимости со старыми данными и пользователями.
- Крупные изображения держать в файлах/хранилище приложения; SQLite использовать для метаданных и путей. Не добавлять новые большие Base64 payloads в SQLite.
- Белый/clay-рендер нужен как вход текущей генерации. Не вводить новое постоянное хранение исходных рендеров без отдельной продуктовой причины. Не удалять и не мигрировать автоматически уже существующие изображения/данные.
- Секреты API хранить через защищённое хранилище Windows, не писать их в логи, frontend storage или документацию.
- Все действия с файлами и сетью валидировать: тип, размер, URL, таймауты, ошибки. Не исполнять импортированные промпты и не отправлять пользовательские изображения во внешнюю сеть без явного выбранного сценария.
- ComfyUI должен общаться с приложением через локальный API. Обнаруживать модели и узлы по доступному серверу; не считать наличие файла на диске доказательством совместимости.
- Показывать честный прогресс backend-задачи. Не рассчитывать проценты по таймеру и не выдавать оценку времени за фактический статус очереди.
- При недоступном провайдере показывать ясную ошибку и способ восстановить соединение; не подменять пользовательский исходник искусственным примером.
- Gemini Web Bridge оставлять полуавтоматическим и управляемым пользователем. Не обходить авторизацию, CAPTCHA, лимиты, paywall и не автоматизировать закрытые API.
- Не добавлять модели, скачивания, тяжёлые зависимости или платные API без явного требования.
- Не отправлять сообщения и не публиковать/загружать изменения в GitHub без прямого поручения. Не делать commit/push автоматически.
- Старые и новые генерации, пользовательские настройки и материалы защищать от случайной потери. Деструктивное удаление делать только по явной команде и с ясным подтверждением.

## Будущий перенос на другой движок

Перенос пока не входит в текущую разработку. Чтобы в будущем снизить его стоимость:

- Держать сборку промптов, бизнес-правила и модели данных независимыми от Electron UI.
- Ограничивать renderer/main общение небольшими типизированными API вместо доступа к Node.js из UI.
- По мере обычной разработки отделять бизнес-логику от Electron IPC, но не создавать абстракции «на всякий случай» и не ломать стабильный текущий workflow.
- Перед миграцией составить инвентаризацию функций, форматов проектов, таблиц, IPC и файлов, а затем согласовать поэтапный план с импортом существующих данных.
