## Технологии старой версии

- Electron 34, React 19, TypeScript 5.7, Vite 6, Tailwind 3.
- `sql.js` хранит SQLite-файл в Electron main process; React обращается к БД через IPC. При недоступности IPC часть данных уходит в `localStorage`.
- Изображения местами сохраняются в SQLite в Base64 или в IndexedDB; материалы-подсказки проекта включают их изображения.
- Есть адаптеры ComfyUI и Gemini API, а также другие облачные AI-провайдеры. Это не соответствует новому принципу «локальные ComfyUI и ручный браузерный Gemini как основной путь; платный API — необязателен».
- Новая целевая архитектура из ТЗ — Rust/Tauri 2 + React/TypeScript + SQLite. В старой папке нет Cargo/Tauri-проекта.

## Что работает по коду и что нельзя считать подтверждённым

- `src/services/promptBuilder.ts` содержит каталоги и `buildSmartPrompt` / `buildArchitecturalPositivePrompt`; `GenerationStudioView.tsx` пересобирает текст при изменении полей и передаёт его провайдеру.
- Gemini-провайдер прикладывает изображения материалов, если они присутствуют. ComfyUI-адаптер строит отдельное diffusion-описание и workflow. Это подтверждает наличие кода интеграции, но не подтверждает качество результата или совместимость текущей конфигурации оборудования.
- Документация старого проекта заявляет функции, которые нужно проверять отдельно на живой установке (например, «точное» сохранение геометрии и прогресс). Не превращать рекламные значения в критерии новой версии.
- В истории запусков есть строка промпта, модель, провайдер и часть параметров; связь именно с версионированным шаблоном отсутствует.
- Не найден отдельный API/модуль пользовательских категорий промптов, импорта из сети, валидатора переменных, безопасного предпросмотра импорта или истории версий.

## Риски и ошибки, которые новая система должна исключить

1. Смешение текста промпта и параметров workflow: denoise, steps, ControlNet и LoRA должны идти структурированными параметрами ComfyUI, а не текстовыми инструкциями.
2. Один длинный текст для всех моделей: ComfyUI и Gemini требуют разных форматтеров, с общей моделью данных и приоритетов.
3. Неподтверждённые обещания «100%/98% Geometry Lock»: diffusion и image editing могут менять геометрию; показывать режим как предпочтение/контроль, не гарантию.
4. Скрытая потеря данных при fallback: пустые `catch` и дублирование БД/localStorage усложняют предсказуемое сохранение.
5. Большие Base64-изображения в БД: в новой версии хранить файлы в управляемой папке, в SQLite — URI/путь, метаданные и связи.
6. Небезопасный сетевой импорт: только HTTP(S), ограниченный размер/таймаут, без исполнения содержимого, без обхода логина/paywall/CAPTCHA, с подтверждением перед импортом.
7. Запросы к внешним источникам не должны включать изображения проектов или личные данные.
8. Неизвестные `{{variables}}`, дубли и конфликтующие инструкции должны выявляться до генерации; внешний текст не может переопределить системные ограничения.

## Новый формат данных шаблона

Хранить шаблон как запись с устойчивым `id`, `name`, `category`, `intent`, `body`, `language`, `tags`, `compatible_engines`, `priority`, `enabled`, `favorite`, `source` (тип/URL/название), `imported_at`, `version`, `parent_id`, `original_body`, `modified_at`. Изменения вести в отдельной таблице версий с авторством действия (импорт/редактирование/обновление), а оценки запуска — отдельной записью, связанной с ID и версией шаблона.

Параметры конкретного запуска (тип комнаты, стиль, режим, свет, материалы, маски/референсы, пользовательская инструкция) хранить структурированно отдельно от шаблона. Сборщик подставляет только разрешённые имена переменных, сообщает об неизвестных и пустых обязательных полях, затем формирует профильный вывод:

- **ComfyUI:** позитивный/негативный текст отдельно от JSON-параметров workflow (модель, ControlNet, denoise, sampler, seed и т. п.).
- **Gemini:** структурированные естественно-языковые инструкции и изображения-референсы; без синтаксиса diffusion. Отправка через ручной браузерный сценарий — базовый бесплатный путь; API — только необязательная настройка с ясным предупреждением о тарификации.

Порядок сборки: явные указания пользователя → разрешённые изменения выбранного режима → ограничения архитектуры для невыбранных объектов → материалы/маски → стиль → качество. Явно выбранный объект разрешено менять, при этом остальные ограничения сохраняются.

## План реализации по этапам

### Этап 0 — аудит и границы (выполнен)

Инвентаризировать старую систему, зафиксировать переносимые данные/функции и ограничения. Старый проект не менялся.

### Этап 1 — локальное ядро Prompt Engine

Описать Rust-модели шаблона, версии, запуска и оценки; SQLite-миграции; встроенные базовые шаблоны категорий; разрешённые переменные и валидатор; детерминированный подбор по категории/тегам/движку/приоритету. Без интернет-импорта и без вызова LLM. Отдельно решить, как редактировать шаблоны, просматривать итог и сохранять использованную версию.

### Этап 2 — адаптеры сборки

Профили ComfyUI и Gemini, тестовые текстовые примеры сборки, интерфейс полей из проекта/материалов. Сборщик возвращает не только строку, но структуру результата и ошибки валидации. Перед интеграцией проверить актуальные workflow и ручной Gemini-сценарий на реальном окружении.

### Этап 3 — UI редактора и локальные файлы

CRUD, поиск, категории, теги, избранное, импорт JSON/Markdown/TXT с предварительным просмотром, проверкой дублей, размера, неизвестных переменных и конфликтных инструкций. Подтверждение импортируемых строк пользователем.

### Этап 4 — внешние публичные источники

GitHub API/raw для выбранного репозитория/файлов и ограниченное извлечение открытого текста URL. Показывать найденные кандидаты до импорта. Добавить ограничения размера, таймаут, проверку URL и ручной ввод при неудаче. Не выполнять скрипты/инструкции из источников.

### Этап 5 — версии, оценки и перенос данных

Сравнение импортированной и локально изменённой редакций с ручным подтверждением обновления; локальные оценки запуска и причины плохого результата; экспорт шаблонов. Отдельный read-only экспортёр из старой БД/данных должен сначала показать план миграции и копировать только выбранные записи после согласования схемы; старую папку не изменять.

## Минимальная первая рабочая версия

1. Локальная база шаблонов и редактор (создать/изменить/дублировать/удалить/искать/категоризировать).
2. Строгие разрешённые переменные и предпросмотр итогового промпта.
3. Предсказуемый подбор без LLM.
4. Раздельные форматтеры ComfyUI и Gemini.
5. JSON/Markdown/TXT импорт с подтверждением, проверкой переменных и дублей.
6. Сохранение версии применённого шаблона в записи генерации.

GitHub и веб-импорт, история сравнения версий, оценки и ручное обновление — следующий этап, после локального ядра. Реализация редактирования области, полноценные библиотеки декора, апскейлер и новый AI-инференс не входят в первую версию Prompt Engine.

Antigravity можно использовать как дополнительную IDE/агента для ограниченных задач по этому новому проекту: например, подготовить форму редактора, описать SQLite-миграцию или сделать отдельный компонент интерфейса. Рабочий порядок: Codex формулирует задачу с точными файлами, границами и критериями готовности; Antigravity меняет только выделенную область; затем Codex читает diff, проверяет архитектуру, безопасность, интеграцию и результат сборки по запросу пользователя. Не передавать ему большие несвязанные задачи и не считать его отчёт о тестах подтверждением без просмотра результата.

Для исключения конфликтующих одновременных правок агенты должны работать последовательно либо в отдельных Git-ветках/worktree с последующим просмотром diff. Не давать Antigravity доступ к старой папке `D:\AI\Project\Visual AI` на запись; целевой каталог — только новый проект. Секреты, API-ключи и реальные клиентские проекты не включать в контекст. Сетевые/MCP-инструменты подключать только если конкретная задача требует их.
